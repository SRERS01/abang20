## Part A: Network Segmentation, Access Controls, Hardening & Sandboxing

### 1. Network Segmentation
* **Concept:** Dividing networks into isolated zones (VLANs, Subnets, VPCs, DMZs) to contain breaches and stop lateral movement.
* **Practical Task:**
  ```bash
  docker network create --internal --subnet=10.40.1.0/24 restricted_zone
  docker network inspect restricted_zone | grep -E "Name|Internal|Subnet"
  docker network rm restricted_zone
  ```

### 2. Access Controls
* **Concept:** Enforcing **DAC** (Discretionary—owner controls ACLs), **MAC** (Mandatory—OS kernel/SELinux security labels), **RBAC** (Role-Based), **ABAC** (Attribute-Based), and **Rule-Based** access policies.
* **Practical Task:**
  ```bash
  touch sensitive_report.txt && chmod 640 sensitive_report.txt && ls -l sensitive_report.txt
  ```

### 3. System Hardening
* **Concept:** Reducing the attack surface by disabling unused ports/services, removing default accounts, enforcing password/SSH policies, and applying CIS Benchmarks.
* **Practical Task (Audit Listening Ports & SSH Hardening Settings):**
  ```bash
  sudo ss -tulnp
  sudo grep -E "^PermitRootLogin|^PasswordAuthentication" /etc/ssh/sshd_config 2>/dev/null
  ```

### 4. Sandboxing
* **Concept:** Running untrusted files, suspicious attachments, or untrusted code inside an isolated, disposable environment (VM or locked container) so malware cannot infect the host OS.
* **Practical Task (Detonate a Script Safely Inside an Ephemeral Network-Isolated Container):**
  ```bash
  docker run --rm --network=none --read-only --cap-drop=ALL alpine:latest \
    sh -c 'echo "Executing untrusted payload inside zero-network sandbox"'
  ```

## Part B: Deception Technologies & Monitoring

### 5. Honeypots, 6. Honeynets, 7. Honeyfiles, 8. Honeytokens & 9. Canary Accounts
* **Concept:** High-fidelity deception traps designed to lure attackers and trigger immediate, zero-false-positive alerts when touched:
  * **Honeypot:** A single decoy server/service (e.g., fake SSH or vulnerable web portal) mimicking real assets to trap attackers and study TTPs.
  * **Honeynet:** A full network of interconnected decoy servers, databases, and simulated user traffic.
  * **Honeyfile:** A decoy file (`passwords_2026.xlsx`, `aws_keys_backup.txt`) placed in shared folders; any `read`/`open` event triggers a SIEM alert.
  * **Honeytoken:** Fake credentials, API keys, or database records planted inside code/configs; any login attempt using that token confirms a breach.
  * **Canary Account:** A decoy high-privilege user account (`adm_backup_sys`) never used by real staff; any authentication attempt immediately alerts the SOC.
* **Practical Task (Deploy a Python Honeyfile Monitor & Canary Account Alert Trigger):**
  ```python
  import os, time

  honeyfile = "passwords_master_2026.txt"
  with open(honeyfile, "w") as f:
      f.write("CANARY_TRAP_DO_NOT_OPEN\n")

  initial_atime = os.stat(honeyfile).st_atime
  # Simulate an attacker reading the honeyfile
  with open(honeyfile, "r") as f:
      _ = f.read()

  if os.stat(honeyfile).st_atime != initial_atime:
      print(f"[CRITICAL - HONEYFILE TRIGGERED] Unauthorized read detected on '{honeyfile}'!")
  os.remove(honeyfile)
  ```

## Part C: Mobile & Application Execution Controls

### 11. Mobile Device Management (MDM)
* **Concept:** Centralized platform enforcing policies on corporate and BYOD smartphones/tablets—requiring passcodes, device encryption, OS patching, **containerization** (separating work vs. personal data), **geofencing**, and **remote wipe**.

### 12. Application Allow Lists vs. 13. Application Block Lists
* **Concept:**
  * **Application Allow List (Whitelisting):** Default-deny posture permitting *only* explicitly approved signed binaries/hashes to run (strongest defense against ransomware/zero-days; e.g., Windows AppLocker / WDAC).
  * **Application Block List (Blacklisting):** Default-allow posture blocking *only* known malicious binaries/hashes.
* **Practical Task (Enforce an Application Allow-List Check in Python):**
  ```python
  allow_list = {"sshd", "nginx", "python3"}
  requested_exec = "mimikatz.exe"
  print("Execution Status:", "PERMITTED" if requested_exec in allow_list else f"BLOCKED ({requested_exec} not in Allow List)")
  ```

## Part D: Intrusion Detection & Prevention (IDS / IPS)

| Technology | Deployment & Core Function |
| :--- | :--- |
| **14. Network-based IDS (NIDS)** | Passive sensor (connected to a switch SPAN/TAP port) analyzing network packets against signatures/anomalies and generating alerts (**does not block**). |
| **15. Network-based IPS (NIPS)** | Placed **inline** on the network path; actively drops malicious packets, resets TCP connections, and blocks attacker IPs in real time. |
| **16. Host-based IDS (HIDS)** | Software agent installed on an individual server/workstation monitoring local OS logs, file integrity (FIM), and registry changes—alerting on anomalies. |
| **17. Host-based IPS (HIPS)** | Software agent installed on an endpoint that actively blocks malicious process injection, unauthorized registry writes, or suspicious syscalls before execution. |
| **18. Wireless IPS (WIPS)** | Dedicated wireless sensor/AP feature monitoring RF spectrum (`2.4/5/6 GHz`) to detect and automatically contain **Rogue APs**, **Evil Twins**, and **Deauth floods**. |

## Part E: Firewalls, Filtering, DLP & Proxies

### 19. Firewalls, 20. Rate Limiting, 21. WAF, 22. Rule-Based Firewalls, 23. UTM & 24. Layer 4 vs. Layer 7 Filtering
* **Concept:**
  * **Rule-Based Firewalls & Layer 4 Filtering:** Filter traffic using Access Control Lists (ACLs) inspecting IP headers and TCP/UDP ports (`IP + Port + Protocol`) and stateful connection tables.
  * **Layer 7 Filtering (NGFW):** Deep Packet Inspection (**DPI**) identifying specific applications (`SSH`, `BitTorrent`, `TLS SNI`) regardless of port number.
  * **Web Application Firewall (WAF):** Protects HTTP/HTTPS web apps from Layer 7 web exploits (**SQLi, XSS, CSRF, Path Traversal**).
  * **Rate Limiting:** Throttling the maximum number of requests per second/minute from a single IP/token to mitigate **DDoS**, **brute-force**, and **API scraping**.
  * **Unified Threat Management (UTM):** All-in-one security appliance combining firewall, IPS, antivirus, content filtering, and VPN (common in SMB/branch offices).
* **Practical Task (Configure Rate-Limiting & Layer 4 Rules in `ufw` + Python API Throttler):**
  ```bash
  # Linux ufw rate-limiting rule (blocks IPs attempting >6 SSH connections within 30 seconds)
  sudo ufw limit 22/tcp 2>/dev/null || echo "ufw rule: limit 22/tcp (anti-brute-force rate limit)"
  ```

### 25. Content Filtering, 26. Data Loss Prevention (DLP) & 27. Proxy Servers
* **Concept:**
  * **Content Filtering:** Blocking access to restricted website categories (malware, phishing, adult, social media) via DNS/URL categorization.
  * **Data Loss Prevention (DLP):** Inspecting data at rest, in motion (email/web uploads), and in use (USB/clipboard) using regex/keywords/labels to block unauthorized exfiltration of PII, PCI, or IP.
  * **Proxy Servers:** Intermediaries that terminate client connections, cache content, enforce URL filtering, hide internal IPs (**Forward Proxy**), or protect and load-balance web servers (**Reverse Proxy**).

## Part F: Endpoint Security & Network Access Control (NAC)

### 28. Endpoint Security, 29. EDR, 30. XDR & 31. Antivirus
* **Concept:**
  * **Antivirus (AV):** Relies primarily on known file signatures and basic heuristics to quarantine known malware.
  * **EDR (Endpoint Detection and Response):** Continuously records endpoint telemetry (process trees, registry, memory, network sockets), detects behavioral IoAs, and allows SOC analysts to **isolate a compromised host** remotely.
  * **XDR (Extended Detection and Response):** Correlates telemetry across **Endpoints + Network + Cloud + Email + Identity** into unified automated incident detection and response.

### 32. Network Access Control (NAC), 33. Captive Portals, 34. 802.1X & 35. Endpoint Compliance
* **Concept:**
  * **NAC:** Enforces authentication and **Endpoint Compliance** posture checks (OS patch level, active EDR, disk encryption) before admitting a device onto the corporate LAN/Wi-Fi. Non-compliant devices are placed into a **Remediation VLAN**.
  * **802.1X:** Port-based network access control standard using **EAP** and a **RADIUS** server to authenticate devices/users via digital certificates or credentials before opening the switch port.
  * **Captive Portals:** Web redirect login/acceptance pages used on guest Wi-Fi, hotels, and airports before granting Internet access.

### 36. Secrets Scanning
* **Concept:** Automated scanning of source code repositories, CI/CD pipelines, container images, and commit histories to detect hardcoded API keys, database passwords, OAuth tokens, and private TLS/SSH keys *before* they are pushed to version control.
* **Practical Task (Build a Pre-Commit Secrets Scanner in Python):**
  ```python
  import re

  staged_files = {
      "config.py": 'AWS_ACCESS_KEY_ID = "AKIAIOSFODNN7EXAMPLE"\nDB_PASS = "Pr0d_Sup3rS3cr3t!"',
      "main.py":   'import os\nDB_PASS = os.getenv("DB_PASS")'
  }

  patterns = {
      "AWS Access Key": r"AKIA[0-9A-Z]{16}",
      "Hardcoded Password": r"(?i)(password|passwd|db_pass|secret)\s*=\s*['\"][^'\"]{8,}['\"]"
  }

  for filename, content in staged_files.items():
      for rule, regex in patterns.items():
          if re.search(regex, content):
              print(f"[SECRETS SCAN BLOCKED] {rule} detected in '{filename}'! Use environment variables or a Vault.")
  ```

### 37. Input Validation
* **Concept:** Strictly verifying that all user-supplied data conforms to expected **data type, length, format, and allow-listed character sets** on the server side *before* processing—stopping **SQL Injection, XSS, OS Command Injection, Buffer Overflows, and Path Traversal** at the boundary.
* **Practical Task (Implement Strict Allow-List Input Validation in Python):**
  ```python
  import re

  def validate_username(username):
      # Allow ONLY 3-16 alphanumeric characters or underscores
      if not re.fullmatch(r"^[a-zA-Z0-9_]{3,16}$", username):
          return f"[REJECTED] Invalid username format: {username!r}"
      return f"[ACCEPTED] Validated username: {username}"

  print(validate_username("ambe_fon26"))
  print(validate_username("admin' OR '1'='1"))
  ```

### 38. Secure Cookies
* **Concept:** Hardening HTTP session cookies against interception, Cross-Site Scripting (XSS) theft, and Cross-Site Request Forgery (CSRF) using three mandatory security attributes:
  * **`Secure`:** Transmits the cookie *only* over encrypted HTTPS connections (never plaintext HTTP).
  * **`HttpOnly`:** Blocks client-side JavaScript (`document.cookie`) from reading the cookie, neutralizing XSS session hijacking.
  * **`SameSite=Strict` (or `Lax`):** Prevents browsers from attaching the session cookie to cross-site requests, mitigating CSRF attacks.
* **Practical Task (Audit an HTTP `Set-Cookie` Header in Python):**
  ```python
  def audit_cookie(header):
      required = ["secure", "httponly", "samesite=strict"]
      missing = [flag for flag in required if flag not in header.lower()]
      return "HARDENED [OK]" if not missing else f"VULNERABLE [!] Missing: {', '.join(missing)}"

  print("Cookie 1:", audit_cookie("sid=99812a; Path=/; Secure; HttpOnly; SameSite=Strict"))
  print("Cookie 2:", audit_cookie("sid=99812a; Path=/"))
  ```

### 39. Static Code Analysis (SAST — Static Application Security Testing)
* **Concept:** Automated white-box analysis of application source code, bytecode, or binaries **without executing the program**. Identifies insecure functions (`strcpy`, `eval()`, `md5`), hardcoded secrets, race conditions, and injection flaws early in the Software Development Life Cycle (SDLC).
* **Practical Task (Use Python's Built-in AST Module to Statically Flag Dangerous `eval()` Calls):**
  ```python
  import ast

  source_code = """
  def process_calc(expr):
      return eval(expr)
  """

  tree = ast.parse(source_code)
  for node in ast.walk(tree):
      if isinstance(node, ast.Call) and getattr(node.func, "id", "") in {"eval", "exec"}:
          print(f"[SAST HIGH SEVERITY] Dangerous function '{node.func.id}()' detected at line {node.lineno}!")
  ```

### 40. Code Signing
* **Concept:** Cryptographically hashing an executable, script, driver, or mobile app and signing the digest with the software publisher's **Private Key** (backed by a trusted Code Signing CA). Operating systems (Windows SmartScreen, macOS Gatekeeper, Linux `apt`/`rpm`) verify the signature before execution to guarantee **Publisher Authenticity** and **Binary Integrity**.
* **Practical Task (Sign & Verify a Deployment Script Using OpenSSL):**
  ```bash
  echo "echo 'Verified Production Update v4.0'" > update_agent.sh
  openssl genpkey -algorithm RSA -out publisher_priv.pem -pkeyopt rsa_keygen_bits:2048 2>/dev/null
  openssl rsa -pubout -in publisher_priv.pem -out publisher_pub.pem 2>/dev/null

  # Sign the script
  openssl dgst -sha256 -sign publisher_priv.pem -out update_agent.sh.sig update_agent.sh

  # Verify signature before execution
  openssl dgst -sha256 -verify publisher_pub.pem -signature update_agent.sh.sig update_agent.sh
  ```

### 41. Email Security: 42. SPF, 43. DKIM, 44. DMARC & 45. BIMI
* **Concept:** Layered DNS and cryptographic controls that stop email domain spoofing, phishing, and Business Email Compromise (BEC):

| Control | How It Works | Key Exam Role |
| :--- | :--- | :--- |
| **42. SPF** *(Sender Policy Framework)* | DNS `TXT` record (`v=spf1 ...`) listing authorized mail server IP addresses/ranges allowed to send mail for the domain. | Validates **sending server IP** against the `Return-Path` domain. |
| **43. DKIM** *(DomainKeys Identified Mail)* | Mail server signs outgoing message headers/body with a **Private Key**; receiving server verifies using the **Public Key** in DNS (`selector._domainkey`). | Proves **message integrity & cryptographic authenticity** even if forwarded. |
| **44. DMARC** *(Domain-based Message Authentication, Reporting & Conformance)* | DNS `TXT` record (`_://domain.com`) enforcing alignment between SPF/DKIM and the visible `From:` header (`p=none`, `p=quarantine`, `p=reject`) + XML reporting. | Instructs receivers how to handle failures (`quarantine`/`reject`) and sends reports. |
| **45. BIMI** *(Brand Indicators for Message Identification)* | DNS record (`default._://domain.com`) pointing to a verified SVG brand logo + Verified Mark Certificate (**VMC**) displayed in user inboxes. | Visually proves brand legitimacy; **requires strict DMARC (`p=quarantine` or `p=reject`)**. |

* **Practical Task (Query Live Production SPF & DMARC Records via CLI):**
  ```bash
  nslookup -type=TXT google.com | grep -i "v=spf1"
  nslookup -type=TXT _://google.com | grep -i "v=DMARC1"
  ```

### 47. SELinux (Security-Enhanced Linux)
* **Concept:** Kernel-level **Mandatory Access Control (MAC)** security module in Linux (RHEL, Fedora, Rocky, Android) that assigns cryptographic security context labels (`user:role:type:level`) to every process, file, and port. Even if a web server (`httpd_t`) is compromised as `root`, SELinux blocks it from reading `/etc/shadow` (`shadow_t`) or writing to unauthorized directories.
  * **Modes:** `Enforcing` (blocks & logs violations), `Permissive` (logs violations without blocking—used for troubleshooting), `Disabled`.
* **Practical Task (Inspect SELinux / AppArmor MAC Status & Security Contexts on Linux):**
  ```bash
  # Check SELinux enforcement mode (or AppArmor on Debian/Ubuntu)
  getenforce 2>/dev/null || sudo aa-status 2>/dev/null | head -n 10

  # View SELinux security context labels (-Z) on system files and running processes
  ls -Z /etc/passwd /etc/shadow 2>/dev/null || true
  ps -eZ | head -n 10 2>/dev/null || true
  ```
