## Part A: Identity Lifecycle, Proofing & Federation Protocols

### 1. User Provisioning, 2. User Deprovisioning & 3. Permission Assignment
* **Concept:**
  * **User Provisioning:** Automated creation of user accounts, mailboxes, and baseline group memberships triggered by HR onboarding workflows (ensuring consistent day-one access).
  * **User Deprovisioning:** Immediate revocation of active sessions, VPN/SSO tokens, API keys, and accounts upon employee termination or contract end—preventing orphaned backdoor access.
  * **Permission Assignment:** Granting access rights strictly aligned with job duties (**Least Privilege**) using group templates rather than ad-hoc individual permissions.
* **Practical Task (Simulate Automated HR Provisioning & Immediate Deprovisioning in Bash):**
  ```bash
  # Create a standard user with a dedicated role group, then safely deprovision
  sudo groupadd -f soc_analysts
  sudo useradd -m -s /bin/bash -G soc_analysts temp_analyst
  id temp_analyst

  # Deprovisioning: Lock account, expire immediately, and remove user + home directory
  sudo usermod -L -e 1 temp_analyst
  sudo userdel -r temp_analyst
  sudo groupdel soc_analysts
  ```

### 4. Identity Proofing
* **Concept:** Verifying that a person is who they claim to be *before* issuing an account, digital certificate, or recovery reset—using government-issued ID verification, live video/biometric liveness checks, or authoritative HR/manager attestation.

### 5. Identity Federation, 6. Single Sign-On (SSO), 7. SAML, 8. LDAP & 9. OAuth
* **Concept:** Protocols enabling centralized authentication and cross-organization access:

| Protocol / Concept | Core Function & Exam Role |
| :--- | :--- |
| **5. Identity Federation** | Linking a user's digital identity across separate organizations/security domains (e.g., logging into a partner portal using your home university/corporate IdP). |
| **6. Single Sign-On (SSO)** | Authenticating once against a central Identity Provider (IdP) to access multiple integrated apps seamlessly without re-entering passwords. |
| **7. SAML** *(Security Assertion Markup Language)* | **XML-based** open standard for **Enterprise Web SSO**—exchanges digitally signed authentication/authorization assertions between an **IdP** and a **Service Provider (SP)**. |
| **8. LDAP** *(Lightweight Directory Access Protocol)* | Protocol (`TCP/389` plaintext, **`TCP/636` LDAPS over TLS**) for querying and modifying hierarchical directory trees (Active Directory, OpenLDAP). |
| **9. OAuth 2.0** *(Open Authorization)* | **JSON/HTTP token-based authorization framework** allowing users to grant third-party apps scoped API access (e.g., *"Allow App X to read your calendar"*) **without sharing their password** *(paired with **OIDC** for authentication)*. |

## Part B: Account Types (7 Classifications)

| Account Type | Purpose & Security Controls Required |
| :--- | :--- |
| **1. Standard User Accounts** | Everyday non-administrative accounts used for email, browsing, and business apps; cannot install software or alter OS settings. |
| **2. Privileged Accounts** | Elevated accounts (`root`, `Domain Admin`, `Global Admin`) used strictly for administration; protected by **PAM, JIT, MFA, and PAWs**—never used for daily web browsing. |
| **3. Global Accounts** | Cloud or enterprise-wide identities spanning multiple tenants, directories, or regional systems (e.g., Entra ID Global Administrator). |
| **4. Local Accounts** | Accounts stored locally in a single machine's SAM database (Windows) or `/etc/passwd` (Linux)—do not require domain connectivity, useful if AD/IdP is offline. |
| **5. Service Accounts** | Non-human accounts running background daemons, scheduled tasks, or app pools; locked down from interactive login (`nologin`) and managed via **gMSA** or key vaults. |
| **6. Third-Party Accounts** | Accounts issued to external vendors, auditors, or contractors; restricted via **time-bound expiration**, MFA, and isolated jump hosts. |
| **7. Emergency Access Accounts** *(Break-Glass Accounts)* | Highly privileged local/cloud recovery accounts excluded from normal SSO/Conditional Access rules in case the primary IdP suffers an outage—stored in a physical/digital vault with **instant SIEM alerting** on any use. |

* **Practical Task (Audit Local vs. System/Service Accounts on Linux / Windows):**
  * **Linux:**

    grep -E "nologin|false" /etc/passwd | head -n 8

  * **Windows (PowerShell):**

## Part C: Multifactor Authentication (MFA — 5 Elements)

Combining at least **two independent authentication factors**: **Something You Know** (password/PIN), **Something You Have** (token/phone/smartcard), **Something You Are** (biometrics), and **Somewhere You Are** (geolocation).

* **1. Hardware Tokens:** Physical **FIDO2/WebAuthn USB/NFC security keys** (YubiKey) or cryptographic smart cards (PIV/CAC). **Gold standard**—immune to Adversary-in-the-Middle (AiTM) phishing proxies.
* **2. Software Tokens:** Mobile authenticator apps (Google Authenticator, Microsoft Authenticator, Authy) generating cryptographic push approvals (with **Number Matching**) or TOTP codes.
* **3. Biometrics:** Physiological (**Fingerprint, Iris/Retina scan, Facial geometry**) or behavioral (**Keystroke dynamics, Gait**) verification. Governed by **FAR** (False Acceptance Rate) and **FRR** (False Rejection Rate) tuned at the **CER** (Crossover Error Rate).
* **4. One-Time Passwords (OTP):** Single-use temporary passcodes—**TOTP** (Time-based, rotates every 30 seconds via shared secret + current timestamp) or **HOTP** (HMAC counter-based).
* **5. Backup Codes:** Pre-generated, single-use recovery codes printed/vaulted during MFA enrollment to regain access if a phone or hardware token is lost.
* **Practical Task (Implement a Working RFC 6238 TOTP Generator in Python):**
  ```python
  import hmac, hashlib, struct, time

  def generate_totp(secret_key_bytes, interval=30):
      counter = int(time.time() // interval)
      msg = struct.pack(">Q", counter)
      digest = hmac.new(secret_key_bytes, msg, hashlib.sha1).digest()
      offset = digest[-1] & 0x0F
      code = (struct.unpack(">I", digest[offset:offset+4]) & 0x7FFFFFFF) % 1_000_000
      return f"{code:06d}"

  shared_secret = b"SecPlusLabMFASecret2026"
  print("Live 6-Digit Software Token (TOTP):", generate_totp(shared_secret))
  ```

## Part D: Access Control Models (6 Models)

| Model | How Access Decisions Are Evaluated | Real-World Example |
| :--- | :--- | :--- |
| **1. Rule-Based** | Evaluates static `IF / THEN` conditions (IP address, port, protocol, geo-location) regardless of user role. | Firewall ACLs (`DENY TCP ANY -> 23`), Conditional Access IP geofencing. |
| **2. Role-Based (RBAC)** | Assigns permissions to **job roles/groups** (`SOC_Analyst`, `HR_Manager`), and users inherit permissions by joining that role. | Active Directory Security Groups, AWS IAM Roles. |
| **3. Time-Based** | Restricts authentication or resource access strictly to approved hours/days or temporary windows. | Blocking contractor VPN logins outside `08:00–18:00` Mon–Fri. |
| **4. Mandatory (MAC)** | OS kernel enforces strict **classification labels** (`Top Secret`, `SELinux contexts`) centrally—users cannot override permissions even on files they own. | Military clearance levels, **SELinux**, **AppArmor**. |
| **5. Discretionary (DAC)** | The **file/resource owner** decides who can read, write, or execute their resource via ACLs. | Standard Windows NTFS permissions, Linux `chmod` / `chown`. |
| **6. Just-in-Time (JIT)** | Grants elevated/privileged access **only on-demand for a brief approved duration** (e.g., 30–60 mins), automatically revoking it afterward (eliminates standing privileges). | Azure PIM / CyberArk temporary admin elevation. |

* **Practical Task (Simulate Time-Based + RBAC + JIT Access Policy Engine in Python):**

      if role == "SysAdmin" and not jit_ticket_active:
          return "DENY: Just-in-Time (JIT) elevation required for production changes"

## Part D: Access Control Models (6 Models)

> **Exam Tip:** CompTIA Security+ scenario questions frequently describe how permissions are granted or restricted and ask you to name the exact model—pay close attention to **who** controls access (the **Owner** in DAC, the **Kernel/Labels** in MAC, **Job Roles** in RBAC, **Static Conditions** in Rule-Based, **Schedules** in Time-Based, or **Temporary Elevation** in JIT).

| Access Control Model | Core Mechanism & Authority | Real-World Technical Example |
| :--- | :--- | :--- |
| **1. Rule-Based Access Control** | Evaluates static `IF / THEN` conditions (IP subnet, port, protocol, device compliance, geo-location) applied globally across subjects. | Perimeter Firewall ACLs (`DENY TCP ANY -> 23`), Azure/Entra Conditional Access IP policies. |
| **2. Role-Based Access Control (RBAC)** | Permissions are bundled into **job roles/groups** (`SOC_Analyst`, `Database_Admin`), and users inherit permissions by being assigned to those roles. | Active Directory Security Groups, AWS IAM Roles, Kubernetes RBAC `ClusterRole`. |
| **3. Time-Based Access Control** | Restricts authentication or resource access strictly to approved business hours, days of the week, or lease windows. | Restricting contractor VPN logins to `08:00–17:00` Monday–Friday. |
| **4. Mandatory Access Control (MAC)** | Centrally enforced by the OS kernel using **classification labels** (`Top Secret`, `Confidential`, `SELinux types`). Users **cannot** change permissions even on files they create. | Government/military clearance systems, **SELinux**, **AppArmor**. |
| **5. Discretionary Access Control (DAC)** | The **file or resource owner** has discretion to set and modify permissions (Read, Write, Execute) for other users via Access Control Lists (ACLs). | Standard Windows NTFS file permissions (`icacls`), Linux `chmod` / `chown`. |
| **6. Just-in-Time (JIT) Access** | Eliminates permanent ("standing") administrative privileges by granting elevated permissions **only on-demand for a short, approved time window** (e.g., 30–60 mins) and automatically revoking them afterward. | Microsoft Entra PIM (Privileged Identity Management), CyberArk ephemeral elevation. |

* **Practical Task 1 (Compare DAC vs. MAC on Linux & Windows):**
  * **Linux (DAC `chmod` vs. MAC `SELinux`):**
    ```bash

    touch dac_demo.txt && chmod 600 dac_demo.txt && ls -l dac_demo.txt

    # MAC: Kernel security context labels enforced centrally
    ls -Z dac_demo.txt 2>/dev/null || echo "MAC enforced via AppArmor/SELinux kernel policy"
    rm -f dac_demo.txt
    ```
  * **Windows (PowerShell — Inspect DAC NTFS ACLs):**
    ```powershell
    Get-Acl C:\Windows\System32\drivers\etc\hosts | Format-List Path, Owner, AccessToString
    ```

* **Practical Task 2 (Simulate a Combined Rule-Based + Time-Based + RBAC + JIT Policy Engine in Python):**
  ```python
  def evaluate_access_request(user, role, src_ip, hour_24, jit_approved):
      # 1. Rule-Based check: Block untrusted external subnet
      if not src_ip.startswith("10.10."):
          return f"DENY [Rule-Based]: Untrusted source IP {src_ip}"

      # 2. Time-Based check: Restrict contractors to business hours (08:00 - 18:00)
      if role == "Contractor" and not (8 <= hour_24 < 18):
          return f"DENY [Time-Based]: Contractor '{user}' outside permitted hours ({hour_24:02d}:00)"

      # 3. RBAC + Just-in-Time (JIT) check: Production DB changes require temporary JIT approval
      if role == "Database_Admin" and not jit_approved:
          return f"DENY [JIT Access]: Standing privileges disabled for '{user}'; activate JIT ticket first"

      return f"ALLOW: Access granted to '{user}' ({role})"

  print(evaluate_access_request("ambe.fon", "Contractor",     "10.10.5.12", 21, False))
  print(evaluate_access_request("grace.n",  "Database_Admin", "10.10.5.20", 14, False))
  print(evaluate_access_request("grace.n",  "Database_Admin", "10.10.5.20", 14, True))
  ```

## Part E: Password Security, Passkeys & Auditing (11 Controls)

### 1. Passkeys & 3. Passwordless Authentication
* **Concept:**
  * **Passwordless Authentication:** Authenticating without typing a traditional password—using FIDO2 hardware keys, platform biometrics (Windows Hello, Touch ID, Face ID), smart cards, or cryptographic push approvals.
  * **Passkeys:** Synced or device-bound **FIDO2 / WebAuthn public-private key pairs** stored inside a device's TPM/Secure Enclave and unlocked locally via biometric/PIN. Because the private key never leaves the device and the signature is cryptographically bound to the exact website domain, Passkeys are **completely immune to phishing, credential stuffing, and server database breaches**.

### 2. Password Managers
* **Concept:** Zero-knowledge encrypted vaults (Bitwarden, 1Password, KeePass) protected by a single strong master passphrase + MFA that generate, store, and autofill unique, high-entropy 20+ character passwords per account—eliminating password reuse and phishing on lookalike domains (since password managers refuse to autofill on mismatched URLs).

### 4. Password Length & 5. Password Complexity
* **Concept:**
  * **Password Length:** The single strongest mathematical defense against offline brute-force GPU cracking (every extra character exponentially multiplies the keyspace; modern **NIST SP 800-63B** standards recommend **14–16+ character passphrases**).
  * **Password Complexity:** Requiring mixed character sets (uppercase, lowercase, numbers, symbols). *Exam Nuance:* Forced complexity combined with frequent expiration causes predictable human patterns (e.g., `Summer2026!`), which is why modern guidance favors **length + banned-password lists** over arbitrary symbol rules.

### 6. Password Reuse, 7. Expiration & 8. Password Age
* **Concept:**
  * **Password Reuse:** Enforcing **Password History** (e.g., remembering the last 12–24 password hashes) so users cannot alternate between two favorite passwords, and educating users never to reuse corporate passwords on personal websites.
  * **Password Age (Minimum & Maximum) & Expiration:**
    * **Minimum Password Age** (e.g., `1–2 days`): Prevents users from immediately changing their password 12 times in a single minute just to clear the password history buffer and reuse their old password!
    * **Maximum Password Age / Expiration** (e.g., `90/180/365 days`): Forces periodic password rotation (note: modern NIST guidelines recommend forcing expiration **only when compromise is suspected or detected**, rather than arbitrary short intervals).

### 9. Compromised Credential Monitoring
* **Concept:** Continuously screening employee emails and password hashes against known dark-web data breach dumps (using services like Have I Been Pwned or Microsoft Entra Password Protection) and immediately forcing a password reset + session revocation when a match is found.

### 10. Account Auditing & 11. Password Policy Reporting
* **Concept:**
  * **Account Auditing:** Regularly reviewing Active Directory / Cloud IAM / Linux accounts for inactive/stale accounts, disabled MFA, accounts with `PasswordNeverExpires` set, and unauthorized privilege escalations.
  * **Password Policy Reporting:** Generating automated compliance reports showing password policy adherence, weak/breached password detections, and MFA enrollment rates for internal governance and external auditors (ISO 27001, PCI-DSS, HIPAA).

  import re

  breached_corpus = {"Password123!", "Welcome2026!", "Admin@2026", "Qwerty123456!"}

  iam_audit_records = [
      {"user": "ambe.fon",      "days_inactive": 4,   "mfa_enabled": True,  "pwd_age_days": 45,  "sample_pwd": "Buea-Mountain-Coffee-2026!"},
      {"user": "legacy_vendor", "days_inactive": 142, "mfa_enabled": False, "pwd_age_days": 410, "sample_pwd": "Welcome2026!"}
  ]

  print("=== IAM ACCOUNT AUDITING & PASSWORD POLICY REPORT ===")
  for acct in iam_audit_records:
      findings = []
      if acct["days_inactive"] > 90:
          findings.append(f"Stale Account ({acct['days_inactive']} days inactive)")
      if not acct["mfa_enabled"]:
          findings.append("MFA Disabled")
      if acct["sample_pwd"] in breached_corpus:
          findings.append("Compromised Credential Match")
      if len(acct["sample_pwd"]) < 14:
          findings.append("Password Length < 14 chars")

      status = "COMPLIANT [OK]" if not findings else "NON-COMPLIANT [!] -> " + "; ".join(findings)
      print(f"User: {acct['user']:<15} | {status}")
