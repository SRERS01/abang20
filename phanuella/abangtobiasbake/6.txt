You're referring to dynamic exploitation tools: tools that interact with an Android application while it is running, examine its behaviour, and test whether vulnerabilities can be exploited.

These are different from JADX and APKTool, which primarily examine application files.

Here are the major tools used in authorised Android penetration testing.

### 2\. Tools for testing live network and API behaviour

| Tool         | Live testing capability                    |
| ------------ | ------------------------------------------ |
| mitmproxy    | Inspect and modify supported HTTP requests |
| OWASP ZAP    | Intercept and test API traffic             |
| Wireshark    | Observe network packets                    |
| HTTP Toolkit | Inspect HTTP communication                 |
| Insomnia     | Send independent API test requests         |
| Postman      | Test API endpoints and responses           |

### 3\. Tools for testing live application logic

| Tool                    | What it helps investigate                    |
| ----------------------- | -------------------------------------------- |
| Frida                   | Runtime method execution and values          |
| Objection               | Runtime application inspection               |
| Appium                  | Automated user interactions                  |
| UI Automator            | Android interface and component testing      |
| LLDB                    | Native application debugging                 |
| Android Studio Debugger | Debuggable Java/Kotlin application execution |
| GDB                     | Native process debugging where supported     |

### 4\. What can these tools test?

Consider a deliberately vulnerable test banking application.

| Security test               | Suitable tools             |
| --------------------------- | -------------------------- |
| Authentication weaknesses   | Frida, Appium              |
| Session handling            | Frida, ADB, API clients    |
| Insecure local storage      | Objection, ADB, SQLite     |
| Exported activities         | Drozer, ADB                |
| Insecure content providers  | Drozer, ADB                |
| API authorization           | mitmproxy, ZAP, Postman    |
| Business logic              | Appium, Frida, API clients |
| Runtime secrets exposure    | Frida, Objection           |
| Native code vulnerabilities | GDB, LLDB, Frida           |
| Network security            | Wireshark, mitmproxy       |

### 5\. Install the core runtime tools on Ubuntu

```bash
sudo apt update
sudo apt install -y adb python3 python3-venv git
```

Create an environment:

```bash
python3 -m venv ~/android-runtime-lab
source ~/android-runtime-lab/bin/activate
```

Install Frida and Objection:

```bash
pip install --upgrade pip
pip install frida-tools objection
```

Verify:

```bash
frida --version
objection --help
frida-ps --help
```

Connect the emulator:

```bash
adb devices
```

Frida requires a compatible Frida server or supported Gadget setup inside the test environment. Its version must match the client version. Root access is commonly needed for system-wide instrumentation on an emulator.

### 6\. Understand the difference between the three levels

Level 1

User-interface interaction

Appium and UI Automator interact with the app as a user would: tapping, typing and scrolling.

Level 2

Runtime interaction

Frida and Objection investigate what happens inside the running application.

Level 3

Security testing and exploitation

Drozer, Frida and API testing tools help establish whether weaknesses in the application or its backend can be demonstrated.

My recommendation: Learn Frida, Objection, Drozer and Appium first. Together, they cover much of the live Android application testing workflow.

One distinction matters: a tool that can hook a running app does not automatically mean it can bypass every security control. Results depend on Android version, root status, application protections and the particular vulnerability being tested.
