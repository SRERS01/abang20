Many things can prevent Nmap from discovering a host, identifying its ports, or detecting its services. Some block Nmap completely; others only hide particular information.

Here is a comprehensive classification for network-security research.

### 1\. Network-level obstacles

| Obstacle             | How it affects Nmap                             |
| -------------------- | ----------------------------------------------- |
| Network firewall     | Blocks incoming or outgoing scan traffic        |
| Host firewall        | Blocks probes arriving at the target            |
| Router ACL           | Filters packets according to network rules      |
| ISP filtering        | Blocks or restricts certain traffic             |
| NAT                  | Hides internal devices behind a public IP       |
| CGNAT                | Shares a public IP among multiple customers     |
| VLAN isolation       | Prevents communication between network segments |
| Network segmentation | Restricts access between different networks     |
| Routing failure      | Prevents packets reaching their destination     |
| Incorrect gateway    | Sends traffic through the wrong route           |
| Asymmetric routing   | Responses take a different network path         |
| Packet loss          | Causes probes or responses to disappear         |
| ICMP filtering       | Prevents some host-discovery methods            |
| TCP filtering        | Blocks TCP probes                               |
| UDP filtering        | Blocks UDP probes                               |
| IPv6 filtering       | Prevents IPv6 connectivity or discovery         |

### 2\. Host-level security controls

These controls operate on the target machine itself.

| Control                                 | Effect                                          |
| --------------------------------------- | ----------------------------------------------- |
| UFW                                     | Filters incoming and outgoing traffic on Linux  |
| iptables                                | Applies packet-filtering rules                  |
| nftables                                | Applies Linux firewall rules                    |
| Windows Defender Firewall               | Filters network connections                     |
| firewalld                               | Manages Linux firewall policies                 |
| SELinux                                 | Enforces access-control policies                |
| AppArmor                                | Restricts application capabilities              |
| Endpoint Detection and Response (EDR)   | May detect or block suspicious scanning         |
| Host Intrusion Prevention System (HIPS) | May block suspicious network activity           |
| TCP wrappers                            | Restrict access to supported services           |
| Fail2ban                                | Can block IPs after triggering configured rules |

### 4\. Port and service-related obstacles

These affect what Nmap can identify.

| Condition                           | Nmap observation                                    |
| ----------------------------------- | --------------------------------------------------- |
| No service listening                | Closed port                                         |
| Firewall silently drops packets     | Filtered port                                       |
| Firewall rejects packets            | Often filtered or closed, depending on response     |
| Service binds only to localhost     | Not externally reachable                            |
| Service listens on a different port | Expected port appears closed                        |
| Service is temporarily unavailable  | Inconsistent results                                |
| Rate limiting                       | Some probes may be dropped                          |
| TLS configuration problems          | Service detection or TLS inspection may be affected |
| Proxy-only access                   | Direct access to the origin may not work            |

### 5\. Host-discovery obstacles

Nmap uses different probes to determine whether a host is online.

Some obstacles include:

* ICMP echo blocking.

* TCP SYN probe filtering.

* TCP ACK probe filtering.

* UDP probe filtering.

* ARP restrictions.

* IPv6 Neighbor Discovery restrictions.

* VPN isolation.

* Wireless client isolation.

* Sleeping or powered-off devices.

* Temporary network disconnection.

An important distinction: a failed host-discovery probe does not necessarily mean the machine is offline.

### 6\. DNS and hostname obstacles

| Problem               | Effect                                                         |
| --------------------- | -------------------------------------------------------------- |
| NXDOMAIN              | Hostname does not exist in DNS                                 |
| Incorrect A record    | Resolves to the wrong IPv4 address                             |
| Incorrect AAAA record | Resolves to the wrong IPv6 address                             |
| DNS propagation       | Different resolvers may return different answers               |
| Split-horizon DNS     | Internal and external networks resolve different addresses     |
| DNS filtering         | Queries may be blocked                                         |
| DNS timeout           | Nmap may not resolve the hostname                              |
| Cloudflare proxy      | DNS may return Cloudflare edge addresses instead of the origin |

### 8\. Nmap's own limitations

Not every unsuccessful scan is caused by security protection.

| Limitation              | Explanation                                         |
| ----------------------- | --------------------------------------------------- |
| Wrong hostname          | Nmap scans the wrong target                         |
| Wrong IP address        | The intended server is not scanned                  |
| Wrong interface         | Traffic uses an unexpected network interface        |
| Missing privileges      | Some scan types require elevated privileges         |
| Incorrect target syntax | Nmap cannot interpret the target                    |
| Wrong port selection    | The service's port is not included                  |
| DNS resolution failure  | Hostname cannot be resolved                         |
| Unsupported protocol    | The requested scan does not test that protocol      |
| Scan timing             | A short timeout may miss slow responses             |
| Outdated Nmap           | Some newer services may not be identified correctly |

### 9\. How to identify what is preventing your scan

For your Ubuntu lab, use this diagnostic sequence.

A. Check your network interface

```bash
ip addr
```

B. Check your routing

```bash
ip route
```

C. Check DNS

```bash
dig api.example.com
```

D. Check basic connectivity

```bash
ping -c 4 api.example.com
```

E. Check TCP connectivity

```bash
nc -vz api.example.com 443
```

F. Run Nmap host discovery

```bash
nmap -sn api.example.com
```

G. Attempt a port scan without host discovery

```bash
sudo nmap -Pn -sS -p 443 api.example.com
```

H. Identify the service

```bash
sudo nmap -Pn -sV -p 443 api.example.com
```

Only run these against systems you own or have explicit authorization to assess.

### 10\. Understand the three important Nmap results

Open

Service accepting connections

A service is listening and accepting connections on that port.

Closed

No listening service

The host responded, but no service is listening on that port.

Filtered

Uncertain

Nmap cannot determine whether the port is open because packet filtering or another network condition prevents a conclusive response.

My recommendation: As a security researcher, learn to distinguish between network reachability, port availability, service identification and application authorization. They are four different testing layers.

Nmap cannot independently overcome every restriction, and a security researcher should investigate the relevant firewall, routing, DNS or cloud configuration through authorized access rather than trying to defeat protections on systems they do not administer.
