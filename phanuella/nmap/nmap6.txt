### Complete network security assessment using Nmap, tcpdump, Wireshark, TShark and Snort

This guide combines all five tools into one practical penetration-testing workflow for your Ubuntu and Android virtual-phone laboratory.

The objective is to teach you how to:

* Discover devices on a network.

* Identify exposed ports and services.

* Identify vulnerable service configurations.

* Capture network traffic.

* Inspect IP, TCP, UDP, DNS and TLS protocols.

* Identify information leakage.

* Detect suspicious network activity.

* Investigate known attack patterns.

* Verify security weaknesses.

* Produce a professional vulnerability assessment report.

Important: These tools primarily assess network-layer and service-level security. They cannot independently discover every application vulnerability, such as IDOR, SQL injection, business-logic flaws or insecure Android storage. Those require additional testing.

Use the commands against your own devices, applications and authorized lab targets.

### 3\. Prepare your Ubuntu environment

### Step 1: Install all five tools

```bash
sudo apt update

sudo apt install -y \
nmap \
tcpdump \
wireshark \
tshark \
snort
```

Check their versions:

```bash
nmap --version
tcpdump --version
wireshark --version
tshark --version
snort -V
```

Snort versions 2 and 3 have different configuration formats. The commands below use the common Snort 3 configuration approach where applicable.

### Step 2: Identify your network interface

```bash
ip -br addr
```

Example:

```text
lo       UNKNOWN 127.0.0.1/8
enp0s3   UP      192.168.1.20/24
```

Your example network details:

```text
Interface: enp0s3
IP:        192.168.1.20
Subnet:    192.168.1.0/24
```

Confirm your route:

```bash
ip route
```

### Step 3: Define your lab variables

```bash
export INTERFACE="enp0s3"
export TARGET="192.168.1.50"
export SUBNET="192.168.1.0/24"
```

Replace these example values with your actual authorized lab details.

### Step 4: Create an evidence directory

```bash
mkdir -p ~/network-security-lab/{scans,captures,reports}
```

This will hold your scan results, packet captures and reports.

### 4\. Phase one: Discover all devices

Primary tool: Nmap

Your first objective is to establish which devices are active.

### Step 1: Discover active hosts

```bash
sudo nmap -sn "$SUBNET"
```

This identifies responsive hosts without performing a port scan.

### Step 2: Identify your target's open TCP ports

```bash
sudo nmap -sS "$TARGET"
```

### Step 3: Scan all TCP ports

```bash
sudo nmap -p- "$TARGET"
```

### Step 4: Check common UDP services

```bash
sudo nmap -sU --top-ports 100 "$TARGET"
```

### Step 5: Identify service versions

```bash
sudo nmap -sV "$TARGET"
```

### Step 6: Save the results

```bash
sudo nmap -sV -oA \
~/network-security-lab/scans/initial \
"$TARGET"
```

### What vulnerabilities can this phase reveal?

* Unnecessary exposed services.

* Exposed administrative interfaces.

* Unexpected database ports.

* Legacy remote administration protocols.

* Outdated service versions.

* Unexpected services accessible from your network.

Example interpretation:

```text
PORT     STATE SERVICE VERSION
21/tcp   open  ftp
22/tcp   open  ssh
23/tcp   open  telnet
80/tcp   open  http
443/tcp  open  https
3306/tcp open  mysql
```

This tells you what services are exposed. It does not prove that FTP, SSH or MySQL is vulnerable.

### 5\. Phase two: Investigate individual services

Primary tool: Nmap

Now investigate whether the exposed services have insecure configurations.

### A. FTP

Potential findings:

* Anonymous FTP access.

* Plaintext authentication.

* Unnecessary FTP service.

* Insecure FTP configuration.

Check anonymous access:

```bash
nmap -p21 --script ftp-anon "$TARGET"
```

Capture FTP traffic:

```bash
sudo tcpdump -i "$INTERFACE" \
-nn -s0 -A 'host 192.168.1.50 and tcp port 21'
```

Wireshark filter:

```wireshark
ftp || ftp-data
```

Look for FTP authentication commands and determine whether credentials are transmitted without encryption.

### B. SSH

Potential findings:

* Weak cryptographic algorithms.

* Outdated SSH implementation.

* Unnecessary remote administration exposure.

* Weak host-key configuration.

Commands:

```bash
nmap -p22 -sV "$TARGET"
```

```bash
nmap -p22 --script ssh2-enum-algos "$TARGET"
```

```bash
nmap -p22 --script ssh-hostkey "$TARGET"
```

Wireshark filter:

```wireshark
ssh
```

You can inspect the SSH handshake and algorithm negotiation, but you cannot normally read encrypted SSH session contents.

### C. Telnet

Potential findings:

* Insecure remote administration.

* Plaintext credentials.

* Unencrypted administrative commands.

Check:

```bash
nmap -p23 -sV "$TARGET"
```

Wireshark:

```wireshark
telnet
```

A successful demonstration of plaintext credential exposure is evidence of a real confidentiality weakness.

### D. SMB

Potential findings:

* SMBv1 support.

* Insecure SMB security configuration.

* Unnecessary file-sharing exposure.

* Unexpected SMB services.

Commands:

```bash
nmap -p445 --script smb-protocols "$TARGET"
```

```bash
nmap -p445 --script smb-security-mode "$TARGET"
```

Wireshark:

```wireshark
smb || smb2
```

### E. DNS

Potential findings:

* Unrestricted recursion.

* Unauthorized DNS zone transfer.

* Internal DNS information disclosure.

* Unexpected DNS server communication.

Commands:

```bash
nmap -sU -p53 \
--script dns-recursion "$TARGET"
```

For a domain you administer:

```bash
nmap -p53 \
--script dns-zone-transfer \
--script-args dns-zone-transfer.domain=lab.example \
"$TARGET"
```

Wireshark:

```wireshark
dns
```

### F. TLS and certificates

Potential findings:

* Deprecated TLS versions.

* Weak cipher suites.

* Expired certificates.

* Incorrect certificate hostnames.

* Insecure cryptographic configuration.

Commands:

```bash
nmap -p443 --script ssl-cert "$TARGET"
```

```bash
nmap -p443 --script ssl-enum-ciphers "$TARGET"
```

Wireshark:

```wireshark
tls.handshake
```

Inspect the protocol version, certificate details, cipher negotiation and handshake failures.

### G. HTTP

Potential findings:

* Unencrypted HTTP communication.

* Unnecessary HTTP methods.

* Server information disclosure.

* Missing or insecure response headers.

Commands:

```bash
nmap -p80 --script http-headers "$TARGET"
```

```bash
nmap -p80 --script http-methods "$TARGET"
```

```bash
nmap -p80 --script http-title "$TARGET"
```

Wireshark:

```wireshark
http
```

Check whether sensitive information is exposed in HTTP requests or responses.

### H. Database services

Investigate exposed database ports:

```bash
nmap -p1433,1521,3306,5432,6379 "$TARGET"
```

Potential issues:

* Database exposed to an untrusted network.

* Administrative interfaces unnecessarily accessible.

* Legacy database versions.

* Insecure database communication.

Nmap identifies exposure; authentication and authorization testing are needed to establish further weaknesses.

### 6\. Phase three: Capture network traffic

Primary tool: tcpdump

You now need packet evidence from the services you have discovered.

Open another Ubuntu terminal.

### A. Capture all traffic to and from the target

```bash
sudo tcpdump \
-i "$INTERFACE" \
-nn -s0 \
host "$TARGET" \
-w ~/network-security-lab/captures/target.pcap
```

Leave it running while you perform your authorized tests.

Press `CTRL+C` when finished.

### B. Capture TCP traffic

```bash
sudo tcpdump -i "$INTERFACE" \
-nn 'host 192.168.1.50 and tcp'
```

### C. Capture UDP traffic

```bash
sudo tcpdump -i "$INTERFACE" \
-nn 'host 192.168.1.50 and udp'
```

### D. Capture DNS

```bash
sudo tcpdump -i "$INTERFACE" \
-nn 'port 53'
```

### E. Capture ICMP

```bash
sudo tcpdump -i "$INTERFACE" \
-nn icmp
```

### F. Capture ARP

```bash
sudo tcpdump -i "$INTERFACE" \
-nn arp
```

### G. Capture TCP SYN packets

```bash
sudo tcpdump -i "$INTERFACE" \
-nn 'tcp[tcpflags] & tcp-syn != 0'
```

### H. Capture traffic on multiple interfaces

For a system where the `any` interface is supported:

```bash
sudo tcpdump -i any -nn -w all-interfaces.pcap
```

What are you looking for?

* Unencrypted authentication.

* Unexpected communication.

* Unusual connections.

* Unexpected DNS destinations.

* Conflicting ARP information.

* TCP connection anomalies.

* Network traffic to unnecessary services.

One limitation: promiscuous mode does not automatically allow you to see all traffic on a switched network. Capture at an appropriate endpoint, bridge, virtual interface or authorized monitoring port.

### 7\. Phase four: Deep packet inspection

Primary tool: Wireshark

Open your capture:

```bash
wireshark ~/network-security-lab/captures/target.pcap
```

Investigate the following areas.

### A. IP-header investigation

Display filter:

```wireshark
ip
```

Inspect:

| IP field        | What to investigate        |
| --------------- | -------------------------- |
| Source IP       | Unexpected sending devices |
| Destination IP  | Unexpected destinations    |
| TTL             | Routing behaviour          |
| Protocol        | TCP, UDP or ICMP           |
| Identification  | Packet identification      |
| Flags           | Fragmentation behaviour    |
| Fragment offset | Packet fragmentation       |
| Total length    | Packet size                |
| Header checksum | Header integrity           |

IPv6 filter:

```wireshark
ipv6
```

Potential findings include unexpected IP communication, unusual fragmentation and suspicious source-address behaviour.

### B. TCP-header investigation

```wireshark
tcp
```

Useful filters:

```wireshark
tcp.flags.syn == 1
```

```wireshark
tcp.flags.reset == 1
```

```wireshark
tcp.flags.fin == 1
```

```wireshark
tcp.analysis.retransmission
```

```wireshark
tcp.analysis.duplicate_ack
```

Investigate:

* Unexpected connection attempts.

* Repeated resets.

* Abnormal connection termination.

* Retransmissions.

* Suspicious scanning patterns.

These are indicators for investigation, not automatic proof of vulnerabilities.

### C. DNS investigation

```wireshark
dns
```

Look for:

* Unexpected domains.

* Internal hostnames exposed to external resolvers.

* Unexpected DNS servers.

* Unusual query frequency.

* Suspicious DNS response patterns.

### D. ARP investigation

```wireshark
arp
```

Investigate:

* Duplicate IP addresses.

* Multiple MAC addresses associated with one IP.

* Unexpected changes in gateway MAC addresses.

* Repeated unsolicited ARP replies.

Potential finding: ARP spoofing or address conflict.

You must verify the legitimate network configuration before classifying it as an attack.

### E. TLS investigation

```wireshark
tls
```

Look at:

* ClientHello.

* ServerHello.

* Supported TLS versions.

* Negotiated cipher suites.

* Certificate information.

* Handshake failures.

Encrypted application contents remain unreadable unless you have an authorized decryption method and the necessary session secrets.

### F. HTTP investigation

```wireshark
http
```

Look for:

* Sensitive information transmitted without encryption.

* Authentication information in visible requests.

* Unexpected HTTP destinations.

* Information disclosure in response headers.

* Unnecessary HTTP communication.

### G. Follow a complete TCP conversation

Right-click a TCP packet and select:

`Follow → TCP Stream`

This helps reconstruct a supported conversation in both directions.

### 8\. Phase five: Automated investigation

Primary tool: TShark

TShark uses the same display-filter engine as Wireshark, making it particularly useful for repeatable investigations. Wireshark +1

### A. List communicating IP endpoints

```bash
tshark -r target.pcap \
-q -z endpoints,ip
```

### B. Identify TCP conversations

```bash
tshark -r target.pcap \
-q -z conv,tcp
```

### C. Extract IP headers

```bash
tshark -r target.pcap \
-Y ip -T fields \
-e frame.number \
-e ip.src \
-e ip.dst \
-e ip.ttl \
-e ip.proto \
-e ip.len \
-e ip.id \
-e ip.flags \
-e ip.frag_offset
```

### D. Extract TCP information

```bash
tshark -r target.pcap \
-Y tcp -T fields \
-e ip.src \
-e tcp.srcport \
-e ip.dst \
-e tcp.dstport \
-e tcp.flags \
-e tcp.window_size_value
```

### E. Identify DNS queries

```bash
tshark -r target.pcap \
-Y dns -T fields \
-e frame.time \
-e ip.src \
-e dns.qry.name
```

### F. Identify HTTP requests

```bash
tshark -r target.pcap \
-Y http.request -T fields \
-e ip.src \
-e ip.dst \
-e http.request.method \
-e http.host \
-e http.request.uri
```

### G. Identify TLS handshakes

```bash
tshark -r target.pcap \
-Y tls.handshake -T fields \
-e ip.src \
-e ip.dst \
-e tls.handshake.type \
-e tls.handshake.version
```

### H. Identify TCP retransmissions

```bash
tshark -r target.pcap \
-Y tcp.analysis.retransmission
```

### I. Identify TCP resets

```bash
tshark -r target.pcap \
-Y 'tcp.flags.reset == 1'
```

### J. Generate protocol hierarchy

```bash
tshark -r target.pcap \
-q -z io,phs
```

### K. Export results to a CSV file

```bash
tshark -r target.pcap \
-Y ip -T fields \
-E header=y -E separator=, \
-e frame.number \
-e ip.src \
-e ip.dst \
-e ip.ttl \
-e ip.proto \
-e ip.len \
> ~/network-security-lab/reports/ip-analysis.csv
```

This allows you to compare traffic from multiple assessments.

### 9\. Phase six: Intrusion detection with Snort

Primary tool: Snort

This is where you introduce network attack detection.

Unlike Nmap, which actively probes services, Snort observes traffic and compares it with configured detection rules.

Snort 3 supports live interface monitoring and PCAP analysis. Snort 3 Rule Writing Guide +1

### A. Check your Snort version

```bash
snort -V
```

Find the configuration file:

```bash
sudo find /etc/snort -maxdepth 2 -type f
```

For Snort 3, a common configuration filename is:

```text
/etc/snort/snort.lua
```

For Snort 2, it is commonly:

```text
/etc/snort/snort.conf
```

Do not use a Snort 2 configuration with Snort 3.

### B. Validate the Snort 3 configuration

If you have Snort 3 and the Lua configuration:

```bash
sudo snort -T \
-c /etc/snort/snort.lua
```

### C. Monitor live traffic

```bash
sudo snort \
-c /etc/snort/snort.lua \
-i "$INTERFACE" \
-A alert_fast
```

This runs passive monitoring and displays alerts generated by the loaded rules.

### D. Analyse your saved PCAP

```bash
sudo snort \
-c /etc/snort/snort.lua \
-r ~/network-security-lab/captures/target.pcap \
-A alert_fast
```

This lets you investigate the same captured traffic with Snort.

### E. Enable a separate local rules file

Create:

```bash
sudo nano /etc/snort/local.rules
```

For a harmless example, add a rule that detects ICMP echo requests in your lab:

```text
alert icmp any any -> any any (msg:"LAB ICMP Echo Request"; itype:8; sid:1000001; rev:1;)
```

This is a demonstration detection rule, not a vulnerability detector.

Validate the configuration and rule file:

```bash
sudo snort -T \
-c /etc/snort/snort.lua \
-R /etc/snort/local.rules
```

Test it against your PCAP:

```bash
sudo snort \
-c /etc/snort/snort.lua \
-R /etc/snort/local.rules \
-r ~/network-security-lab/captures/target.pcap \
-A alert_fast
```

If the package does not provide Snort 3 or the expected configuration, check its installed version and package documentation before using these commands. Snort 2 requires different configuration and rule-loading syntax.

### F. What can you investigate with Snort?

| Investigation            | What you look for                    |
| ------------------------ | ------------------------------------ |
| Port scanning            | Repeated connection attempts         |
| Suspicious DNS           | Matches against configured DNS rules |
| Known exploit attempts   | Signatures of known exploits         |
| Suspicious HTTP requests | Recognized attack patterns           |
| Malware communication    | Known malicious traffic signatures   |
| Network reconnaissance   | Suspicious probing behaviour         |
| Policy violations        | Traffic matching prohibited patterns |
| ICMP anomalies           | Unusual ICMP patterns                |

Snort alerts are leads, not proof. Investigate the matching packet in Wireshark and confirm whether the activity is genuinely malicious.

Important: Running Snort in passive IDS mode does not block attacks. Inline IPS operation requires supported packet-acquisition modules, correct network placement and carefully tested configuration. Snort 3 Rule Writing Guide +1

### 10\. Phase seven: Nmap vulnerability detection

Nmap has a scripting engine called NSE (Nmap Scripting Engine).

It allows you to perform additional checks against discovered services. Some scripts identify specific known vulnerabilities; others inspect configurations or retrieve information. Nmap Network Scanning +1

### A. Find available vulnerability scripts

```bash
ls /usr/share/nmap/scripts/*vuln*.nse
```

Search for a particular script:

```bash
ls /usr/share/nmap/scripts/ | grep -E 'ssl|smb|ftp|http|dns|ssh'
```

Read the description of a script:

```bash
nmap --script-help ssl-enum-ciphers
```

### B. Check known vulnerabilities

For an authorized test host, use carefully selected NSE scripts relevant to its detected services.

For example:

```bash
sudo nmap -sV \
-p21,22,80,443,445 \
--script ftp-anon,ssh2-enum-algos,ssl-cert,ssl-enum-ciphers,smb-protocols \
-oA ~/network-security-lab/scans/service-checks \
"$TARGET"
```

Nmap also has a `vulners` script that can correlate identified software versions with known vulnerability information when the script and external service are available. It does not prove that a CVE is exploitable on your target. Nmap Scripting Engine documentation +1

Avoid blindly running all NSE scripts. Some scripts can be intrusive or disruptive, particularly those categorized as `dos`, `exploit`, `brute` or `intrusive`. Nmap Network Scanning

| Network policy violations        | Custom rules              |
| ICMP anomalies                   | ICMP rules                |
| Known attack traffic             | Signature-based detection |

Remember: Snort only detects activity covered by its active rules and visible to its sensor.

### 12\. How to combine all five tools in one assessment

This is the workflow I recommend using in your Ubuntu laboratory.

### Integrated network security assessment

* Nmap — Discovery

    Discover devices, ports, services and versions.

    Output: Nmap scan results

* tcpdump — Capture

    Capture the traffic generated during the assessment.

    Output: PCAP file

* Wireshark — Investigation

    Inspect packet headers, application protocols, TLS and network behaviour.

    Output: Packet-level evidence

* TShark — Automation

    Extract endpoints, DNS queries, TCP conversations and protocol statistics.

    Output: Structured analysis

* Snort — Detection

    Analyze the captured traffic against security rules.

    Output: Intrusion detection alerts

* Verification and reporting

    Confirm findings, determine impact, document evidence and recommend remediation.

### Example: Investigating a suspicious open service

Suppose Nmap identifies port 23 open.

* Nmap establishes that Telnet is exposed.

* tcpdump captures the Telnet communication.

* Wireshark examines whether authentication data is transmitted in plaintext.

* TShark extracts the source, destination and relevant traffic fields.

* Snort can alert on Telnet traffic if the appropriate detection rules are configured.

* You document the exposure and demonstrate the confidentiality risk using your own test credentials.

This is how you turn a simple discovery into a properly evidenced security finding.

### 14\. How to classify your findings

Not every observation deserves a vulnerability report.

| Severity      | Example                                                                     |
| ------------- | --------------------------------------------------------------------------- |
| Critical      | Confirmed severe unauthorized compromise                                    |
| High          | Unauthorized access to sensitive systems or information                     |
| Medium        | Significant security weakness with limited or conditional impact            |
| Low           | Minor information disclosure or limited security weakness                   |
| Informational | Open port or configuration observation without demonstrated security impact |

Use the actual impact and exploitability to determine severity, not the tool's output alone.
